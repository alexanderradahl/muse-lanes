# muse-lanes v0.3: one lead, a fleet of Muse lanes

Status: plan, 2026-11-06, revised after a review against the mods docs (overview, interface, events, api, test,
troubleshoot, reference). Branch `feat/v03-fleet`.

## Goal

One Claude lead runs about 7 Muse lanes directly ("lead > muse", no Opus lane session in between) and follows
them all in the Claude Code UI. Each lane does a full implementation. The plugin tells the lead when something
needs a decision and stays quiet otherwise. The lead keeps merging, box assignment and final review.

## Lessons this design answers

| Night of 2026-11-05/06 | v0.3 answer |
| --- | --- |
| Consult helpers made calls that belong to the lead | Advisor and Muse helper may answer `ESCALATE:`; the runner turns it into a `question` needs-lead event |
| 5 h lost to a gate waiting on a leased box | Box queue with a wait budget; past it, a `box_wait_timeout` event wakes the lead while the lane keeps its place |
| Two `pgrep -f` waiters deadlocked | Box queue uses ticket files plus the lane's own supervisor lock (pid + start time), never process names |
| Status polls stacked (fixed 0.2.2), answers lost (0.2.3), PASS skipped fix round (0.2.3) | Kept; new fields are added to the cheap path only for live lanes |

## Ownership (where the meaning lives)

- **Runner (`bin/muse-lane`)** owns lane state and every typed fact: needs-lead events, box tickets, scope
  check, evidence. It is the only writer of lane files. Deterministic, tested in `bin/test_muse_lane.py`.
- **Accept script** owns what an accept failure means. It reports through exit codes mapped in config, or a
  `LANE-NEEDS-LEAD: <kind> <detail>` line. The runner does not guess from log text.
- **Advisor / helper model** owns judgment on a consult question, including whether it is a lead decision
  (`ESCALATE:`). The runner records the escalation as a typed fact; it does not judge the question.
- **Hook (`hooks/index.tsx`)** owns presentation and waking: panel, status line, toasts, digest prompt. It
  reads runner JSON and never infers state the runner did not report.
- **Project adapter (config file)** owns project specifics: lease file format, accept exit codes, box wait
  budget, advisor command. SimGoodie's lives in `examples/simgoodie.json`; the core names no SimGoodie path.

## Config

`$MUSE_LANES_CONFIG`, else `<lanes root>/config.json`, else defaults. Read by the runner at `start` (copied
into `lane.json` so a running lane never changes under the lead) and by `boxes`.

```json
{
  "accept_exit_kinds": { "5": "accept_failed_harness", "6": "box_wait_timeout" },
  "box_wait_max_min": 30,
  "lease_file": "~/r12-master/LEASES.md",
  "lease_claim_re": "^(?P<at>\\S+) CLAIM (?P<box>\\S+) by (?P<who>[^:]+): (?P<what>.*)$",
  "lease_release_re": "^(?P<at>\\S+) RELEASE (?P<box>\\S+) by ",
  "advisor_cmd": ["claude", "-p", "--model", "{model}", "--tools", "Read,Grep,Glob",
                  "--permission-mode", "dontAsk", "--no-session-persistence",
                  "--settings", "{\"disableAllHooks\":true}"],
  "advisor_timeout_min": 15
}
```

Unknown keys are ignored; a malformed file is a `start` error naming the key.

## 1. Lane fleet and needs-lead events

### New lane/state fields (status JSON)

```ts
needs_lead: null | { seq: number; kind: NeedsLeadKind; detail: string; at: string; step?: number }
needs_lead_announced: boolean        // marker announced-lead-<seq> exists for the current seq
box: string | null                    // from lane_start
box_state: null | 'queued' | 'held'
box_queued_at: string | null
branch: string | null                 // live lanes only (cheap path), null when ended
head: string | null                   // live lanes only
evidence: null | {                    // set when the lane ends done
  branch: string; head: string; head_start: string; commits: number;
  accept_log: string; review_files: string[]; summary_path: string }
advisor_calls: number
```

`NeedsLeadKind` is exactly: `question`, `review_failed`, `accept_failed_code`, `accept_failed_harness`,
`box_wait_timeout`, `scope_violation`.

Consult entries gain `by: 'muse' | 'claude-sonnet' | 'claude-opus'` and `escalated: boolean`.

### When each kind is raised

| Kind | Raised when | Lane after |
| --- | --- | --- |
| `question` | A consult answer's first line is `ESCALATE: <reason>` | Keeps running; `ANSWER.md` says the lead was asked and to continue other work or wait |
| `review_failed` | Pre-review FAIL after the last fix round | Ends `review_failed` (as today) |
| `accept_failed_code` | Accept exits nonzero and no mapping or line says otherwise | Ends `failed` |
| `accept_failed_harness` | Exit code mapped to it, or `LANE-NEEDS-LEAD: accept_failed_harness ...` | Ends `failed` |
| `box_wait_timeout` | Box ticket waited past `box_wait_max_min`, or accept exit mapped to it | Queue wait: keeps waiting. Accept exit: ends `failed` |
| `scope_violation` | After a step, a changed path (committed since `head_start` or dirty) matches no `scope` glob | Ends `failed`, paths in `detail` |

`LANE-NEEDS-LEAD:` lines in accept output follow the same `^LANE-NEEDS-LEAD: (\S+) ?(.*)$` shape as
`LANE-PHASE:`; the last one wins, and an unknown kind is recorded as `accept_failed_code` with the raw line in
`detail`. Each raise increments `seq`. A new raise replaces an unacknowledged one; the wake reports the latest.

### Runner commands

- `ack <id> --lead <seq>`: claims the needs-lead announcement for that seq (marker `announced-lead-<seq>`,
  exit 3 if already claimed), like `ack` and `--orphan` today.
- `answer <id> [--text T | --text-file F] [--box B]`: the lead's reply. With text, writes `.lane/ANSWER.md`
  (and `ANSWER-lead-<seq>.md`), clears `needs_lead` if it is a `question`, logs it in `consults` with
  `by: 'lead'`. With `--box`, moves the lane's ticket to the back of box B's queue (a fresh stamp: keeping the
  old one would let it pass a lane already holding B) and clears a `box_wait_timeout`. Refuses on an ended lane
  and while the lane holds its box. While the supervisor lives, `answer` never rewrites `state.json`: it writes
  a sidecar the supervisor merges on its next poll, so the two writers cannot overwrite each other.
- `boxes --json`: one object per box seen in tickets or the lease file:
  `{ box, holder_lane, queue: [lane ids in order], lease: null | { who, what, since } }`.
  The lease is the last CLAIM line for the box with no later RELEASE.

### Waking (hook)

Each poll gathers this session's pending announcements: ended lanes not announced, current needs-lead seqs not
acknowledged, orphans not announced. Each goes into an outbox kept in `$.state` (`muse.outbox`, so a module
reload keeps it) before `ack` claims it; an ack another session won takes it back out. One prompt then carries the
whole outbox:

- one item: the full text as today (summary for an ended lane; kind, detail and the answer command for a
  needs-lead event);
- several: a digest headed `Muse: N lane events`, one block per lane (label, id, status, needs-lead kind and
  detail, or the ready-to-merge evidence), and a pointer to `lane_summary <id>`.

The submit is never awaited: it resolves only when the turn starts, and awaiting it inside the poll would freeze
the pane and status line for the whole of a busy turn (mods api docs). Entries leave the outbox as the prompt is queued, so a reload while it waits for its turn never
sends them twice. A submit that resolves `{ drop }` or rejects (an interrupt, a hook's refusal) puts them back,
retried after 20 s, doubling to 10 min while drops repeat. Events claimed while a submit is on its way go out
in the next prompt. Limit: a queued prompt that the host drops after a reload or a session restart is lost;
`lane_status` still shows the lane.

Routine progress (phase changes, commits, a step finishing) never wakes. A lane that ends `done` reads
**READY TO MERGE** with its evidence (branch, head, commits, accept log, review files). The lead merges
through its own train merge script; the plugin never merges.

## 2. Advisor

`lane_start` takes `advisor: { model?: 'sonnet' | 'opus', max?: number }` (defaults sonnet, 3 per lane).
With an advisor set, a consult goes to `advisor_cmd` (with `{model}` filled) instead of the Muse helper while
`advisor_calls < max`; past the budget it falls back to the Muse helper and the existing `consult_max`.

- Read-only: `--tools Read,Grep,Glob` and hooks disabled; `start` refuses an `advisor_cmd` whose tools include
  Bash, Edit, Write or NotebookEdit. There is no git before/after guard: Muse keeps working while a consult runs,
  so its own edits would trip one.
- An advisor failure or timeout falls back to the Muse helper for the same question, with the advisor's error
  logged (the CLI on the owner's Mac has hit its weekly limit once).
- Bounded: `advisor_timeout_min`, the answer capped at 8,000 characters in `ANSWER.md`.
- The advisor brief states the lane's accept command and scope and says it may not change either: a question
  that needs a different acceptance, scope or a product decision is answered `ESCALATE: <one line>`. Row
  `muse-lanes-consult-changes-acceptance` stands: only the lead changes acceptance.
- Logged in `consults` with `by` and `escalated`, and in the summary. The advisor binary is `$CLAUDE_BIN` or
  `advisor_cmd[0]`, so tests use a fake.

## 3. Boxes

`lane_start` takes `box: string`. Before its accept (and each fix-round accept), the supervisor takes a ticket
`<root>/_boxes/<box>/<queued_at>-<lane_id>` and waits until its ticket is the oldest whose lane supervisor is
alive (checked through the lane's lock: pid plus start time, never `pgrep`). It exports `LANE_BOX=<box>` to
the accept, sets phase `box_wait` while queued, holds the box through the accept, then removes its own ticket.
Dead lanes' tickets are skipped, not removed; a starting or resuming supervisor removes its own stale ones.
Past `box_wait_max_min` it raises `box_wait_timeout` once per wait and keeps its place; getting the box clears
it; `answer --box` moves it and restarts the wait clock.

The queue only orders this plugin's lanes. The project's gate script still claims the real box (SimGoodie:
`r16-gate.sh` writes CLAIM/RELEASE in `LEASES.md` and exits 6 on its own wait timeout, mapped above). The
panel shows both the queue and the lease file's holder.

## 4. UI (mods)

- **Pane `muse-lanes`** (docked beside the transcript, `/muse` or auto-opened on the first `lane_start`):
  a header line (`5 running · 2 need lead · 1 ready`), a Boxes section (box, holder, queue, lease), then one
  row per lane, needs-lead first, then this session's working lanes, others, ended:
  a toggle labeled with the flag and lane name, then status, phase + elapsed and idle time; a second line with
  box, total elapsed, review state, commits + last subject; a third with the needs-lead detail or failed accept
  tail. The toggle expands the row (drill-down): the summary for an ended lane or the live status (fetched on
  press), evidence for a done lane, and buttons `stop`, `resume`, `refresh`.
- **Status line:** `muse: <label> <phase>` for one working lane; else `muse: N running · M need lead`.
- **Toasts:** only for needs-lead events and non-`done` endings, never for `done` or progress; 15 s, one toast
  per poll (`Muse: N lanes need the lead` for several). The same text goes to `$.ui.notify`, which reaches a
  terminal's notification channel; it is a no-op in the Desktop app, where the owner's own `Notification`
  settings hook (type `plugin_notification`) can raise an OS banner.
- **Placement:** a pane cannot ask to dock. Opened from `lane_start` (not the person's own command) it is placed
  only from 144 columns; `lane_start` says "/muse shows the lanes pane" when it was not placed.
- **Desktop:** the Desktop app draws only a Button's `label`, so each row is a labeled toggle (`▸`/`▾`)
  beside its text, not a Button wrapping the row.
- **State contract:** `muse.lanes`, `muse.boxes`, `muse.expanded`, `muse.details`, `muse.outbox`,
  `muse.summaryTries`. Render reads only; writes happen in polls and press handlers.
- **Tools:** `lane_start` gains `scope`, `box`, `advisor`; new `lane_answer { id, text?, box? }` and
  `lane_boxes {}`.

## Slices

Runner slices share `bin/muse-lane` and `bin/test_muse_lane.py`, so they run as one Muse lane with three
chained steps (one writer). The hook slice runs in parallel on Opus (UI work), on the other files.

| Slice | Executor | Files | Control branch (breaks production, accept proves the new tests fail on it) |
| --- | --- | --- | --- |
| A needs-lead, config, scope, evidence, `ack --lead`, `answer` | Muse | runner + runner tests | `control/v03-needs-lead`: accept exit kinds ignored |
| B advisor + ESCALATE | Muse | same | `control/v03-advisor`: ESCALATE not raised |
| C box queue + `boxes` | Muse | same | `control/v03-box-queue`: dead-lane tickets block the queue |
| D hook: digest wake, toasts, status, pane, tools, types | Opus | `hooks/index.tsx`, `types/index.d.ts`, `tests/plugin.test.ts` | plugin test against a faked runner; a mutation run shows the digest test fails when two events submit two prompts |
| E docs, example adapter, version 0.3.0 | lead | README, CHANGELOG, `examples/simgoodie.json`, `plugin.json` | — |

Review: Muse pre-review on the runner lane, then the lead reads every diff and reruns the accept; the hook gets
an independent Opus review. `claude plugin validate --strict .` and `claude plugin test .` must pass.

## Out of scope

- The plugin does not merge, pick boxes, or run gates itself.
- No reinstall while the SimGoodie lead's lanes run; the owner installs 0.3.0 between builds.
- Waking a session other than the lane's owner (unchanged known limit).
